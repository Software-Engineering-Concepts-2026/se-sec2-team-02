### 1. หน้าต่างที่แตก (Broken Windows) ในอดีต
จากแนวคิด Software Entropy และ Broken Window Theory "หน้าต่างที่แตก" ที่เคยปล่อยปละละเลยในโปรเจกต์ก่อนๆ คือ **การไม่ยอมเขียนคอมเมนต์อธิบายโค้ดที่ซับซ้อน และการตั้งชื่อตัวแปรแบบลวกๆ (เช่น a, b, c, temp) รวมถึงการปล่อยให้เกิด Duplicate Code (โค้ดซ้ำซ้อน) เพียงเพราะต้องการรีบส่งงานให้ทันเวลา**

**ผลกระทบในระยะยาว:** พอเวลาผ่านไปเรื่อยๆ เมื่อระบบต้องเพิ่มฟีเจอร์ใหม่ การกลับมาอ่านโค้ดเดิมทำได้ยากมาก กลายเป็นว่าทีมต้องเสียเวลาแกะโค้ดเก่าอยู่เป็นวันๆ และพอแก้จุดหนึ่ง ก็ไปพังอีกจุดหนึ่งโดยไม่ตั้งใจ ทำให้ซอฟต์แวร์เสื่อมสภาพลงเรื่อยๆ (Software Entropy) เหมือนตึกที่มีหน้าต่างแตกแล้วไม่มีใครซ่อม จนสุดท้ายคนอื่นๆ ในทีมก็เริ่มเขียนโค้ดแย่ๆ ตามกันไปเพราะคิดว่า "ตรงอื่นก็เละเหมือนกัน"

### 2. การรับผิดชอบและการสื่อสาร (Take Responsibility)
หลักการ **"Take Responsibility"** ในความเข้าใจของฉัน คือการกล้ายืดอกรับผิดชอบต่อหน้าที่และผลลัพธ์ของงานที่ตนเองได้รับมอบหมาย หากเกิดข้อผิดพลาดหรือทำงานไม่ทันตามกำหนด จะไม่มีการหาข้ออ้าง น้ำขุ่นๆ หรือโทษปัจจัยภายนอก (Don't Make Lame Excuses) แต่จะต้องเป็นคนที่ควบคุมสถานการณ์และนำเสนอหนทางแก้ไขปัญหาให้ทีมเดินหน้าต่อได้

**ตัวอย่างสถานการณ์ที่จะนำหลักการ "Provide Options, Don't Make Lame Excuses" ไปใช้ในโปรเจกต์นี้:**
สมมติว่าฉันได้รับมอบหมายให้ทำฟีเจอร์หนึ่ง แต่ติดปัญหาทางเทคนิคทำให้ทำเสร็จไม่ทันตามกำหนดแทนที่จะบอกเพื่อนว่า *"พอดีช่วงนี้งานเยอะมาก คอมก็อืด ฟีเจอร์นี้เลยยังไม่เสร็จนะ"* (ซึ่งเป็น Lame Excuse) 

ฉันจะเปลี่ยนเป็นการสื่อสารแบบให้ทางเลือกกับทีมแทน เช่น:
> "ทุกคนคะ ฟีเจอร์นี้เราติดปัญหาเรื่องเทคนิคบางอย่าง ทำให้ไม่ทันเดดไลน์วันนี้แน่ๆ แต่เราเตรียม **ทางเลือก (Options)** ไว้ให้ทีมพิจารณา 2 ทางค่ะ:
> 1. ขอเลื่อนกำหนดส่งเฉพาะฟีเจอร์นี้ออกไปอีก 2 วัน โดยเราจะรีบเคลียร์ให้จบ
> 2. หรือให้เรา Push โค้ดส่วนที่เสร็จแล้วขึ้นไปก่อน แล้วตัดฟีเจอร์ย่อยบางตัวออกไป เพื่อให้ภาพรวมของทีมยังสามารถเอาไปเดโมต่อได้ทันตามกำหนด
> ทุกคนคิดว่ายังไงดีคะ?"
